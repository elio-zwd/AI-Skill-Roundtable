- 下载文件已按领域整理，详见[分类记录](./候选图片/下载图片分类记录.md)。本轮没有检查图片质量、尺寸或页面覆盖率。

## 2. 工作流与 AI 分工

```text
用户选定本批图片与保留元素
  → 规格 AI：图片 + 原候选描述 + 产品规范 → 可实施规格
  → 开发 AI：规格 + 同一组选定图片 → 运行中的 UI
  → 验收 AI：真实运行截图 + 选定图片 + 规格 → 差异清单
  → 开发 AI 修正 → 同条件截图复验 → 用户验收本批
```

开发 AI 必须同时看到原图和规格。文字负责精确文案、交互与状态，图片负责整体比例和视觉关系；只传文字容易在每次交接中丢失布局信息。

每批完成后再扩展下一批，不必把几十张图全部转写完才开始试做。规格 AI 与验收 AI 可以是不同对话，交接依赖文件而不是聊天记忆。本计划不会自动创建其他 AI 任务。

### 输入冲突的处理

1. 产品行为按 ADR-009、当前术语、产品模型和 PRD；旧 PR08 冲突措辞已被覆盖。
2. 页面结构与视觉按用户选定记录、选定图片、对话视觉基线；候选描述用于补充设计意图。
3. 图片乱码、iOS 元素、未经确认的功能、自动保存成果等不能直接变成产品要求。
4. 图片看不出来的交互写明“建议”或“待确认”，不伪称从图中识别。会影响功能范围的冲突交给用户决定；不受影响部分继续。
5. 现有对话规格中的旧底部导航文字由本轮四项导航覆盖；聊天主体视觉与既有交互继续保留。

## 3. 每批开始前的选图记录

在本目录下建立 `实施规格/<批次>/选图记录.md`。这些目录由后续 AI 在实际处理该批时创建。

每个页面或状态登记：页面 ID、原描述路径、选定图片路径、图片哈希、采用区域、忽略区域、用户要求、决定状态。局部混搭必须明确到区域，不能同时要求还原三套互斥布局。

状态分开记录：已下载 → 已对应页面 → 用户已选定 → 规格已审查 → 已实现 → 截图已验收。前一状态不能推导后一状态。

先核对重复下载、主页面候选、状态组拆图与遗漏项；同名或数量相同不代表一一对应。名称不明的四张由用户手动处理，不要求为了推进本批先处理所有图片。

组件板是组件视觉参考，状态板是测试状态集合，都不是新增一级页面。每个领域边实现页面边完善真实使用的组件，避免预先构建无人使用的大型组件库。

## 5. 规格 AI 的交付要求

使用[单页规格模板](./实施交接/单页实施规格模板.md)，每个实际页面一份；局部 Sheet、Dialog 可随所属页面描述，复杂独立流程单独成文并明确返回关系。

必须包含：

- 页面 ID、选定图、原候选描述、版本与采纳决定。
- 布局顺序、固定/滚动区域、关键尺寸、颜色、文字层级、圆角、图标和头像资产。
- 每个按钮的触发条件、结果、取消、返回、持久化与失败行为。
- 正常、加载、空、搜索无结果、错误、禁用、长文本、键盘遮挡等适用状态；不适用的说明原因。
- 既有能力与新增需求的边界。规格 AI 未检查代码时应标记“待代码核查”。
- 已确认事实、视觉估计、待用户决定分别标注；估计值不能写成精确测量。

1440 × 3200 是设计像素尺寸，不能直接写为 Compose dp。记录实际图片尺寸与内容区域，再依据设备 density、fontScale、安全区和现有主题确定 dp/sp；不能假定固定除以 3。

先复用对话页已确定的颜色、间距与字体语义，再把每页差异写入规格。头像和图标必须有资源路径或资源待办，不让开发 AI 从截图随意重画不同人脸。

## 6. 开发 AI 的施工边界

开工读取根目录和目标目录 AGENTS.md、当前产品规范、批次选图记录与已审查规格。核查最新目标分支、开放 PR 与同文件修改；每任务使用独立分支，避免不同 AI 同时改主题或 App.kt。

当前可定位的代码入口包括 `ui/screens/dialog/`、`skills/`、`resources/`、`settings/`，以及 `ui/navigation/`、`ui/theme/`、`ui/App.kt`。这只是本次文件清单检查结果，不等于所有候选功能已接通；实施前必须沿调用链核查。

先输出每项操作与现有 ViewModel/Repository/测试的对应表。若需新增 Room、网络协议、备份机制等底层能力，将其列为独立功能任务，明确依赖与范围，不能在视觉施工中悄悄扩张。

遵守 Route 收状态与副作用、Screen 接不可变状态和回调、组件只展示与局部交互的分层。共享展示组件归公共组件；不跨域引用页面内部组件。主题统一定义，避免无关依赖升级和两套正式页面。

可以使用 Preview/测试假数据做视觉开发，但生产入口必须接真实状态。未完成项如实报告；不得把截图画成整张背景、把文字烧进图片或把所有按钮写成空回调。

## 7. 截图对比与迭代

每批至少留存：选定参考图、运行截图、截图环境、差异清单、修复后截图。建议后续存入 `实施验收/<批次>/`，文件名含页面 ID、状态、版本；环境记录 Git SHA 和未提交改动说明。

截图条件记录设备/模拟器、分辨率、density、fontScale、系统版本、系统栏模式、应用主题、样例数据、滚动位置和键盘状态。基准目标为 Xiaomi 14 Ultra 竖屏 1440 × 3200；条件不同必须说明。

对比时统一应用内容区域；系统时间、电量、挖孔等由系统负责，不能为匹配生成图在 App 中手绘。允许对齐展示比较，不允许拉伸截图掩盖布局误差。

按顺序处理差异：

1. 页面区域、内容层级、遮挡、固定区与滚动区。
2. 主要控件尺寸、间距、文字层级、头像及卡片比例。
3. 颜色、边框、圆角、图标与弱阴影。

每项差异记录“区域 / 期望 / 实际 / 严重程度 / 修复建议 / 复验结果”。验收 AI 先只读出报告，开发 AI 修复后再复验，不能只说“相似度 95%”。

通过标准：无缺失入口、关键错位或遮挡，精确文案符合规格，功能验收通过；剩余轻微视觉差异列明由用户接受。图片里不合理的布局不能压过 48dp 触摸区、可读性和 Android 系统行为。

对基准屏之外至少检查一款较窄 Android 屏幕和放大字体；表单检查键盘、滚动、取消与系统返回；Modal 检查关闭路径。没有设备或截图环境时写“待运行验收”，不把 Preview 当成真实运行截图。

## 8. 每批完成与交接

生产代码修改至少执行 `compileDebugKotlin`、`testDebugUnitTest`；UI 批次补充 `lintDebug`、`assembleDebug`，按修改风险执行相关 Compose/设备测试。以仓库 AGENTS.md 要求为准，报告真实命令与结果。

每批必须提供：改动文件、规格版本、图片路径、已实现交互、未完成项、实际测试证据、运行截图、差异报告和下一批依赖。编译通过、CI 通过、视觉通过、用户验收分开记录。未经用户授权不合并 PR。

后续 AI 的复制提示词见[接手提示词](./实施交接/AI接手提示词.md)。建议首先派发“规格 AI：我的主页面 B”，完成这一页的规格与用户审查后，再派发开发任务。
