# 见域术语契约

> 文档状态：2026-08-29 当前产品术语契约
>
> 适用范围：目标产品“见域”的用户界面、产品规格、设计稿、帮助文案与跨 PR 协作。
>
> 决策依据：[ADR-009 — “对话 + Skill 角色”产品心智模型与多角色独立性](../decisions/adr-009-skill-role-conversation-product-model.md)。
>
> 覆盖关系：当 PR08 历史文档中的“议题 / 推进议题 / 邀请 Skill / 角色不能替代 Skill”等定义与本文冲突时，以本文和 ADR-009 为准。历史文档继续保留用于追溯，不再覆盖当前用户术语。

## 1. 文档目的

本文统一见域当前的产品语言，避免后续设计和实现再次把用户带回“多智能体控制台”心智。

核心原则只有四条：

1. 用户首先是在 **对话**，不是在管理“议题”。
2. 用户面对的是 **Skill 角色**，不是无人格的 Skill 工具条目。
3. 多个 Skill 角色是 **平级、独立的个体**，不是主从团队，也不是默认正反方。
4. 工程内部可以保留精确结构，但内部术语不能反向污染用户界面。

---

## 2. 使用规则

1. 用户界面、帮助文案和当前产品规格优先使用本文“面向用户的正式名称”。
2. `Skill` 仍可以作为工程和能力建模术语；只要指代正在和用户交流的参与者，用户侧必须写 **Skill 角色** 或具体角色名。
3. “议题”不再是普通用户必须理解的最高层对象；旧 `topic` / `stage` 数据结构可以暂时存在于工程内部。
4. 不使用“主 Skill / 副 Skill / 主角色 / 从属角色”表达多角色关系。
5. 不使用“正方 / 反方”作为新增角色的默认职责。角色的赞同、补充或反驳应由其自身判断自然产生。
6. 用户增加参与者时正式写 **增加 Skill 角色**，不用“邀请 Skill”。
7. 角色排序、头像大小、进入顺序只用于导航和最近互动提示，不表示权力、优先级或谁领导谁。
8. 默认多角色行为是 **独立回应**；只有用户明确引用另一角色或主动触发 **交叉讨论** 时，才把其他角色的观点作为显式讨论输入。
9. 真实人物型 Skill 角色可以高度人物化，但必须在角色详情、首次使用或其他合理位置明确其为 AI 模拟角色/视角，不代表本人。
10. 用户不需要理解 `Agent`、编排器、Run、响应批次、Schema、Interaction ID 等工程概念才能使用产品。

## 3. 核心正式术语

| 面向用户的正式名称 | 内部概念 | 正式定义 | 不等于 |
|---|---|---|---|
| 对话 | `conversation screen` | 见域 Top 1 核心页面。用户与一个或多个 Skill 角色持续交流的主要空间。 | 议题详情、项目工作台、多智能体控制台 |
| 会话 | `conversation/session` | 一段可持续保存、继续、搜索、归档的对话容器，承载消息、参与角色、资料与成果关系。 | 一次模型调用、单条消息、必须分阶段的项目 |
| Skill | `skill capability` | 内部能力包/能力载体，可包含角色设定、领域知识、工具权限、工作流和输出能力。 | 用户侧必须直接看到的“人物”、单次回答 |
| Skill 角色 | `skill role` | 用户实际看见、选择并交流的 AI 角色，是 Skill 能力的角色化呈现，拥有稳定身份、思考方式和表达风格。 | 真人本人、无人格工具按钮、其他角色的下属 |
| 参与 Skill 角色 | `participating roles` | 当前会话中已经由用户确认参与的 Skill 角色集合。 | 主从阵容、所有官方角色、历史角色全集 |
| 增加 Skill 角色 | `add role` | 用户把一个新的 Skill 角色加入当前会话。 | 社交邀请、自动加入、创建下属角色 |
| 移除 Skill 角色 | `remove role` | 用户停止让某个角色继续参与当前会话。 | 删除该角色过去的消息、资料或成果 |
| 本次回复角色 | `directed responder` | 用户通过 `@角色` 或选择器指定当前请求由哪个角色回答。 | 主角色、长期优先级、退出多角色会话 |
| 独立回应 | `independent response` | 角色主要基于用户输入、用户选择的上下文和自身角色设定形成判断，不默认受其他角色刚生成结论影响。 | 隔绝全部会话上下文、互相复制、自动辩论 |
| 交叉讨论 | `explicit cross-discussion` | 用户显式选择参与角色和焦点后，让角色互相看到并回应相关观点的一次协作。 | 默认模式、无限辩论、多数投票 |
| 消息 | `message` | 用户、Skill 角色或系统在会话中的时序内容单元。 | 会话本身、成果、资料 |
| 资料 | `material` | 用户选择带入对话用于理解、核查和判断的文件、链接、摘录、证据或结构化信息。 | 普通 AI 回复、已确认成果、缓存文件 |
| 成果 | `artifact` | 用户明确确认保存的判断、行动方案、知识笔记、沟通稿或其他可复用输出。 | 每条 AI 回复、未确认草稿、导出动作 |
| 个人背景 | `personal context entry` | 用户主动保存、可见、可编辑、可选择带入会话的长期事实、偏好和约束。 | 系统暗中画像、全部历史聊天、自动长期记忆 |
| 继续深入 | `continue deeper` | 用户希望把当前对话继续向某个方向推进、整理或形成下一步的自然入口。 | “推进议题”、强制新阶段、让所有角色重复回答 |
| 对话节点 | `conversation node/stage` | 仅在确有必要的二级历史/结构界面中，用于表示会话内某个明确目标或结构节点。 | Top 1 必须展示的阶段时间线、响应批次 |
| 会话记录 | `conversation history` | 用户搜索、打开、归档和继续已有会话的入口。 | 议题列表、工程日志 |
| 共识 | `consensus` | 多个角色在给定条件下相互一致的部分。 | 多数票、绝对真理 |
| 分歧 | `disagreement` | 不同角色在事实判断、假设、价值取向或建议上的真实差异。 | 系统错误、必须人为制造的“反方” |
| 适用条件 | `applicability conditions` | 某项判断或建议成立所依赖的前提、范围与约束。 | 空洞免责声明、无条件结论 |
| 下一步 | `next action` | 用户可以执行、验证或继续探索的具体行动。 | 自动执行、旧“下一轮”按钮 |

## 4. Skill 与 Skill 角色的边界

### 4.1 Skill 是内部能力，Skill 角色是用户侧参与者

推荐采用以下分层：

```text
Skill 能力层
├── 角色设定 / persona
├── 领域知识与思维框架
├── 可调用工具或工作流
├── 输入/输出能力
└── 风险、来源、时效和权限边界
        ↓ 角色化呈现
Skill 角色
├── 名称
├── 头像 / 肖像
├── 身份与简介
├── 稳定思考方式
├── 稳定表达方式
└── 在会话中的消息与行为
```

只要一个对象要作为聊天参与者出现，就应以 **Skill 角色** 的身份呈现。

纯工具、纯数据处理器或工作流如果并不需要“说话”，可以作为 Skill 角色背后的能力存在，不要求伪装成独立人物。

### 4.2 角色感不是安全问题本身

允许并鼓励角色在 UX 上具有明确的人物感：

- 人物化头像或肖像；
- 稳定姓名；
- 第一人称表达；
- 连贯性格；
- 可识别的思考习惯；
- 不同角色之间明显不同的语言气质。

身份真实性通过适当披露解决，而不是通过把角色做成机械工具来解决。

真实人物型角色的推荐说明：

> AI 模拟角色，基于可获得资料构建，不代表本人，也不保证复现本人当前或完整观点。

该说明适合放在角色详情、首次使用或必要风险提示中；不要求每条消息重复。

不得写成：

- “本人正在与你聊天”；
- “这是本人刚刚给你的建议”；
- “本人已确认/批准这段回答”；

除非是在引用有来源支持的真实历史事实，并且明确区分引用与 AI 生成内容。

## 5. 多角色关系与动作术语

| 正式动作 | 行为 | 不会自动发生的变化 |
|---|---|---|
| 独立回应 | 一个或多个 Skill 角色分别形成自己的判断 | 不默认读取其他角色刚生成的完整结论，不互相复读 |
| @角色 / 本次回复角色 | 当前请求由指定角色回答 | 不提升为主角色，不改变长期参与关系 |
| 增加 Skill 角色 | 用户确认把新角色加入当前会话 | 不设为下属，不默认赋予正/反方，不删除历史 |
| 移除 Skill 角色 | 停止该角色后续参与 | 不删除其历史回答、资料或成果 |
| 交叉讨论 | 用户选择角色和焦点，让相关角色显式回应彼此观点 | 不无限循环，不自动投票，不形成永久主从关系 |
| 整理共识与分歧 | 系统或指定角色整理当前多角色观点 | 不替用户决定，不把少数观点抹掉 |

### 5.1 新增角色的上下文原则

为了保证真正的独立性，新增加的 Skill 角色首次判断默认应获得：

- 用户当前请求；
- 当前会话中必要的用户消息；
- 用户明确选择带入的资料、个人背景和成果；
- 中性的事实背景或会话简报；
- 自身 Skill 角色设定。

默认不应把“前一个角色完整回答”当作它必须继承的领导性结论。

其他角色输出只有在以下情况才成为明确输入：

1. 用户引用、转述或点名要求评价；
2. 用户选择“交叉讨论”；
3. 当前任务本身明确要求比较已有角色观点。

### 5.2 立场自然形成

不要预先把第二个角色命名为“反方顾问”。

同一个角色面对不同问题可以：

- 完全赞同；
- 部分赞同并补充条件；
- 指出不同假设；
- 提出反对意见；
- 认为当前证据不足；
- 提供与前一角色完全不同的分析路径。

这些结果来自角色自身判断，而不是系统强制制造冲突。

## 6. 会话与“继续深入”

### 6.1 会话是用户的持续容器

一个会话可以持续很久，也可以只包含一次简短问答。

会话可以关联：

- 多条用户与角色消息；
- 参与 Skill 角色及变化历史；
- 用户选择的资料与个人背景；
- 已保存成果；
- 可选的内部对话节点/结构关系。

用户不需要为了保存长期上下文而先理解“议题”“阶段”或“响应批次”。

### 6.2 继续深入

“继续深入”是自然的后续动作，不代表每次都创建一个新的正式阶段。

它可以根据场景提供：

- 深入某个问题；
- 换一个角度；
- 增加 Skill 角色；
- 发起交叉讨论；
- 核查关键假设；
- 整理下一步；
- 形成成果。

如果工程为了历史、成果关联或恢复需要创建内部节点，可以在实现层处理，不要求用户先完成“三步推进议题”。

## 7. 资料、成果与个人背景

以下语义继续沿用，不因本次心智模型调整而改变：

| 正式名称 | 规则 |
|---|---|
| 资料 | 是输入和依据，保留来源与使用关系 |
| 已选择资料 | 当前会话/请求明确允许带入的资料 |
| 草稿 | 尚未被用户确认为成果的生成内容 |
| 成果 | 只有用户明确保存后才成为正式成果 |
| 个人背景 | 只有用户主动保存并选择后才用于长期复用 |
| 导出文件 | 数据承载形式，不自动等于业务成果 |
| 恢复快照 | 本地恢复机制，不等于用户成果 |

不能把资料、消息、草稿和正式成果混为同一个对象。

## 8. 高风险与身份表达

### 8.1 可用表达

- “AI 模拟角色，不代表本人。”
- “基于当前资料，我的判断是……”
- “这里有几个条件会改变结论。”
- “请核对来源、时效和适用条件。”
- “重要决定前建议由具备资质的专业人员复核。”

### 8.2 禁止表达

- 未说明 AI 模拟性质时，把真实人物型角色包装成真人本人正在实时交流；
- 把角色生成内容声称为真人本人当前正式意见；
- “这是医学诊断”；
- “这是正式法律意见”；
- “保证收益”或“保证结果”；
- 因为“用户最终决定”而省略必要风险边界。

## 9. 历史术语迁移

| 历史/旧规格用语 | 当前处理 | 迁移规则 |
|---|---|---|
| 议题 | 会话 | 用户侧改为会话；内部 `topic` 可暂留 |
| 议题列表 | 会话记录 | 用户侧历史入口统一改名 |
| 议题详情 / 工作区 | 对话 | Top 1 页面统一改名 |
| 推进议题 | 继续深入 | 不再作为冻结入口名称 |
| 阶段 | 内部结构 / 必要时“对话节点” | 不作为聊天主页面常驻概念 |
| Skill（指聊天参与者） | Skill 角色 | `Skill` 保留为内部能力术语 |
| 角色 / `Character` | Skill 角色的当前工程基础 | 不再要求用户侧反向改成 Skill |
| 当前 Skill 阵容 | 参与 Skill 角色 | 避免“阵容/编队”强化控制台感 |
| 邀请 Skill | 增加 Skill 角色 | 正式用户动作改名 |
| 主 Skill / 副 Skill | 删除 | 多角色默认平级 |
| 默认正方 / 反方 | 删除 | 立场由角色独立判断形成 |
| 临时定向回应 | @角色 / 本次回复角色 | 产品文案更自然 |
| 显式交叉讨论 | 交叉讨论 | 仍要求用户显式触发 |
| 下一轮 / `roundIndex` | 响应批次（内部） | 不作为用户侧对话结构 |
| Run / 执行运行 | 内部执行概念 | 不直接展示给普通用户 |
| 圆桌会议 | 多角色对话 / 交叉讨论（按实际行为） | 圆桌不再作为最高层心智模型 |

## 10. 工程映射

本节只约束语义，不要求本次文档 PR 立即重命名 Kotlin/Room。

| 当前/历史工程对象 | 当前产品关系 | 注意 |
|---|---|---|
| `ChatSession` | 可作为“会话”数据迁移基础 | 是否扩展 Schema 由实现 PR 决定 |
| `Message.chatId` | 消息归属会话的现有基础 | 不意味着资料/成果关系已完整 |
| `Message.roundIndex` | 内部响应批次索引 | 不应继续决定用户侧“阶段”文案 |
| `Character` | Skill 角色的现有实现基础 | 后续可扩展人格、能力、来源和角色元数据 |
| `RoundtableOrchestrator` | 多角色响应调度基础 | 必须审计是否破坏独立回应契约 |
| Interactions `previous_interaction_id` | 模型调用优化机制 | 不应让前一角色回答自动成为后一角色的领导性上下文 |
| `roundtable` Route | 历史路由 | 后续 UI 重构按“对话”页面迁移 |

特别注意：如果实现层为了节省 token 或复用会话链，把前一 Skill 角色的完整生成结果无条件传给下一角色，就可能违反“默认独立回应”契约。后续编排 PR 必须专门审计。

## 11. 文案示例

### 11.1 正确

- “增加 Skill 角色”
- “当前有 3 个 Skill 角色参与”
- “@费曼，你怎么看这个假设？”
- “让这些角色分别独立分析”
- “发起交叉讨论”
- “继续深入”
- “保存为成果”
- “打开会话记录”
- “这个角色是 AI 模拟角色，不代表本人。”

### 11.2 错误

- “邀请一个 Skill 加入阵容”
- “主 Skill 将领导其他 Skill 完成分析”
- “第二个 Skill 默认作为反方”
- “后加入角色必须以上一个角色的结论为基础”
- “推进议题是唯一正式入口”
- “第 3 轮就是第 3 阶段”
- “这位人物本人正在与你聊天”
- “系统自动增加了一个角色并开始调用模型”

## 12. 当前规范优先级

发生定义冲突时，当前产品语义按以下顺序处理：

1. [ADR-009 — “对话 + Skill 角色”产品心智模型与多角色独立性](../decisions/adr-009-skill-role-conversation-product-model.md)；
2. 本文；
3. [见域产品模型](./jianyu-product-model.md)；
4. [见域 PRD](./jianyu-prd.md)；
5. PR08-F 与更早 planning 文档仅作为历史依据。

后续如果再次改变产品心智模型，应新增明确决策记录，不要只在某张 UI 图或某个实现 PR 中静默改词。
