# 见域产品模型

> 文档状态：2026-08-29 当前产品模型
>
> 适用范围：目标产品“见域”的产品对象、用户心智模型与核心行为。
>
> 当前决策基线：[ADR-009 — “对话 + Skill 角色”产品心智模型与多角色独立性](../decisions/adr-009-skill-role-conversation-product-model.md)。
>
> 重要说明：本文定义目标产品，不代表当前 Android 工程已经完成相应迁移，也不冻结 Room Schema、Kotlin 类型、API 名称或路由名。

## 1. 产品定义

> **见域是一款以 AI Skill 角色对话为核心的个人思考与行动应用。用户可以和一个或多个具有独立人格、思维方式与能力边界的 Skill 角色持续交流，在不同观点之间形成自己的判断，并把有价值的内容沉淀为资料、下一步和成果。**

这个定义替代旧 PR08 中“围绕持续议题调用多个 Skill 并分阶段推进”的用户心智模型。

内部仍可以使用多智能体编排、能力包、响应批次、阶段节点等工程结构，但这些结构服务于对话体验，而不是要求用户理解它们。

---

## 2. 冻结原则

1. **对话是 Top 1**：用户打开见域的首要行为是开始或继续对话。
2. **会话是持续容器**：长期保存的用户对象叫“会话”，不是“议题”。
3. **Skill 角色是用户侧参与者**：Skill 是内部能力载体；用户看到和交流的是 Skill 角色。
4. **角色应有真实角色感**：头像、名字、人格、思维方式和表达风格应足够稳定，让角色能力真正发挥出来。
5. **身份必须真实**：高度拟人化不等于冒充真人。真实人物型角色必须在适当位置说明 AI 模拟身份。
6. **多角色平级**：没有默认主 Skill、副 Skill、领导者或下属。
7. **立场独立形成**：系统不预设第二个角色是反方，也不要求后加入角色追随前一个角色。
8. **默认独立回应**：角色首次形成判断时，不默认继承其他角色刚生成的完整结论。
9. **交叉讨论显式触发**：只有用户主动要求，角色才把彼此观点作为明确讨论输入。
10. **用户拥有控制权**：增加/移除角色、带入资料和背景、保存成果、触发交叉讨论等关键动作由用户控制。
11. **聊天内容优先**：控制、状态、运行参数和内部结构不能长期抢占主聊天界面。
12. **目标与现状分离**：文档先冻结产品契约；实现层按后续 PR 逐步迁移。

---

## 3. 核心对象关系

```text
用户开始 / 打开一个会话
        ↓
选择或沿用一个 Skill 角色
        ↓
对话
├── 用户消息
├── Skill 角色 A 的独立回答
├── 可选：增加 Skill 角色 B / C ...
│   ├── B 按自己的设定独立判断
│   └── C 按自己的设定独立判断
├── 可选：@某个角色进行本次定向回复
├── 可选：用户显式发起交叉讨论
├── 可选：带入资料 / 个人背景 / 已有成果
└── 可选：继续深入 / 保存成果
        ↓
会话持续保存，可搜索、继续或归档
```

用户侧不需要先经历“创建议题 → 创建阶段 → 推进议题”的必经流程。

如果实现需要用内部节点组织恢复、成果来源、长上下文或任务状态，可以在数据层维护，但不得把内部模型当作普通用户必须理解的产品模型。

## 4. 核心对象定义

### 4.1 会话

**定义**：一段可持续保存和继续的 AI Skill 角色对话容器。

**会话可以承载**：

- 标题和创建/更新时间；
- 用户消息；
- Skill 角色消息；
- 参与角色及变化历史；
- 用户选择带入的资料；
- 用户选择带入的个人背景；
- 已确认成果；
- 必要的内部上下文/节点关系；
- 生成状态、失败和恢复信息。

**规则**：

- 会话可以只有一个角色，也可以有多个角色；
- 会话不要求固定阶段数；
- 增加/移除角色不删除历史消息；
- 归档会话不等于删除；
- 用户可以重新打开并继续原会话；
- 如果用户需要完全独立的新上下文，可以新建会话。

### 4.2 对话

**定义**：会话的主要交互界面，也是见域 Top 1 核心页面。

**必须突出**：

- 当前会话内容；
- 正在参与的 Skill 角色；
- 每条 AI 消息属于哪个角色；
- 输入、发送、@角色、增加角色等核心动作。

**不应成为主视觉的内容**：

- Run ID；
- 响应批次；
- 编排器状态；
- 上下文确认流水线；
- 默认策略/Override；
- 持久化状态卡；
- 强制阶段时间线；
- 大型“控制与成果面板”。

### 4.3 Skill

**定义**：内部能力单元，为角色提供人格设定、领域知识、思维方法、工具、工作流、输入输出能力以及风险边界。

Skill 可以包含：

- Persona / System Prompt；
- 角色背景和价值取向；
- 领域知识；
- 思维框架；
- 联网搜索能力；
- 工具或工作流；
- 输出格式偏好；
- 来源、时效、许可和安全规则。

Skill 本身不是必须直接暴露给普通用户的工程对象。

### 4.4 Skill 角色

**定义**：Skill 能力在用户侧的角色化呈现，是用户实际交流的参与者。

**一个 Skill 角色至少应具有**：

- 稳定名称；
- 头像或肖像；
- 简短身份说明；
- 明确擅长范围；
- 稳定思维特点；
- 稳定表达风格；
- 可解释的来源/时效/风险信息；
- 独立形成判断的能力。

**角色行为原则**：

- 可以直接表达自己的判断，而不是总以“作为 AI，我……”开头；
- 可以有强烈但一致的风格；
- 可以和其他角色观点相同，也可以不同；
- 不需要为了制造“多样性”而强行反对；
- 不能因为加入顺序变成前一个角色的助手或下属。

### 4.5 真实人物型 Skill 角色

**定义**：基于真实人物公开资料、已知思想、表达风格或历史行为构建的 AI 模拟角色。

**允许**：

- 人物姓名；
- 人物化肖像；
- 第一人称角色表达；
- 稳定模拟其公开可观察的思考风格。

**身份边界**：

在角色详情、首次使用或其他合理位置清楚说明：

> AI 模拟角色，基于可获得资料构建，不代表本人，也不保证复现本人当前或完整观点。

主聊天区不需要每条消息重复这段说明，但不得把 AI 生成内容伪装成真人本人当前真实发言、授权或背书。

### 4.6 消息

**定义**：用户、Skill 角色或系统在会话中产生的时序内容单元。

消息应保留：

- 发送者；
- 时间与顺序；
- 内容；
- 生成/失败/停止状态；
- 必要的引用和来源；
- 与资料或成果的关系。

Skill 角色消息必须能够一眼识别角色身份，不应全部显示成同一个“AI”发送者。

### 4.7 资料

**定义**：用户选择用于理解、核查和回答当前会话的文件、链接、摘录、证据或结构化信息。

规则：

- 资料是输入和依据，不是成果；
- 用户应知道当前哪些资料会被带入；
- 资料保留来源和使用关系；
- 系统可以推荐资料，但不应未经用户允许把敏感资料发送给所有角色。

### 4.8 个人背景

**定义**：用户主动保存、可编辑、可选择复用的长期事实、偏好和约束。

规则：

- 默认不等于“系统自动画像”；
- 用户可决定是否带入当前会话；
- 角色只应获得当前请求真正需要的背景；
- 删除或停用背景不能静默改写历史消息。

### 4.9 成果

**定义**：用户明确确认保存的可复用输出。

可以包括：

- 判断/决策记录；
- 行动方案；
- 知识笔记；
- 沟通文本；
- 研究摘要；
- 文档结构；
- 其他可交付内容；
- 音频等派生形式。

普通 Skill 角色回复不自动成为成果。系统可以建议“保存为成果”，最终由用户确认。

## 5. 多 Skill 角色模型

### 5.1 平级参与

多个参与角色之间默认没有组织层级。

```text
用户
├── Skill 角色 A
├── Skill 角色 B
└── Skill 角色 C
```

不是：

```text
用户
└── 主 Skill
    ├── 副 Skill B
    └── 副 Skill C
```

角色之间的差异来自各自 persona、知识、证据、风险偏好和推理方式，不来自固定上下级关系。

### 5.2 增加 Skill 角色

用户可以在会话中随时 **增加 Skill 角色**。

新增后：

- 新角色成为平级参与者；
- 不自动改变既有角色身份；
- 不删除过去消息；
- 不默认扮演反方；
- 不默认继承前一个角色的结论；
- 可以在后续消息中被 @点名。

系统可以推荐适合增加的角色，并说明推荐理由，但不得未经用户确认自动加入并开始调用。

### 5.3 默认独立回应

多角色的关键价值是“真实差异”，不是“多人一起复读同一个思路”。

因此默认独立回应时，每个角色的首次判断主要输入应来自：

```text
用户问题 / 用户消息
+ 用户选择资料
+ 用户选择个人背景
+ 必要的中性会话事实
+ 角色自己的 Skill 设定
```

而不是：

```text
前一个 Skill 角色的完整答案
→ 作为后一个角色必须继承的上下文
→ 再让后一个角色回答
```

后者容易形成锚定、模仿、从众和虚假共识。

实现层可以为了连贯性提供中性的事实简报，但应避免把前一角色结论包装成“已确定前提”。

### 5.4 @角色 / 本次回复角色

用户可以：

- 输入 `@角色名`；
- 点击角色头像后选择“让 TA 回答”；
- 通过回复对象选择器指定本次角色。

定向只影响当前请求，不产生长期主角色。

### 5.5 交叉讨论

交叉讨论是**显式模式**。

触发后，用户至少可以确认：

- 哪些角色参与；
- 讨论哪个问题/哪条消息；
- 是否只讨论一轮或进行有限轮次。

交叉讨论允许角色看到其他角色相关观点并进行回应。

完成后：

- 不改变角色长期身份；
- 不产生永久领导者；
- 默认恢复独立判断；
- 结果可以整理共识、分歧、适用条件和下一步；
- 不通过多数票判断真理。

### 5.6 不预设正反方

“思维拓展”可以得到反对意见，但反对意见应来自真实推理。

例如新角色可能认为：

- 前一个角色整体正确，只需要补充；
- 前一个角色的前提有问题；
- 结论方向正确但风险估计不足；
- 两者关注的时间尺度不同；
- 现有证据不足，暂时不应下结论。

系统不应为了制造戏剧冲突强制角色站队。

## 6. 上下文与角色独立性

### 6.1 上下文分层

建议将会话上下文拆成：

1. **用户上下文**：用户消息、明确目标、约束；
2. **资料上下文**：用户选择的文件、链接、证据；
3. **个人背景**：用户明确允许带入的长期背景；
4. **角色私有设定**：该 Skill 角色自己的 persona/能力；
5. **其他角色输出**：其他角色生成的观点；
6. **系统运行信息**：模型、工具、Interaction ID、失败状态等。

默认独立回应应主要使用 1～4；第 5 类只有在用户明确引用、比较或发起交叉讨论时才应作为显式观点输入；第 6 类不属于普通用户内容。

### 6.2 Interactions / 会话链实现注意

工程可以使用 Interactions API、缓存或 `previous_interaction_id` 降低 token 开销，但**优化不能改变产品语义**。

如果复用同一模型会话链会把角色 A 的回答无条件注入角色 B 的上下文，就需要：

- 为角色隔离会话链；或
- 构建角色独立上下文；或
- 在编排层明确过滤其他角色输出。

具体技术方案由实现 PR 决定，但验收标准是：B 的默认回答不能因为 A 先发言而被系统性锚定。

## 7. “继续深入”与内部节点

旧规格把“推进议题”定义成唯一正式阶段入口。本模型不再要求用户以项目/阶段方式组织所有对话。

用户侧自然入口为 **继续深入**。

“继续深入”可以打开一组与当前上下文相关的动作，例如：

- 深入当前问题；
- 检查一个关键假设；
- 增加 Skill 角色；
- 换一个视角；
- 发起交叉讨论；
- 整理下一步；
- 形成成果。

内部如果仍需要 stage/node 来支持：

- 长会话压缩；
- 恢复；
- 成果来源追踪；
- 任务工作流；
- 历史结构化浏览；

可以保留为内部对象。只有当用户确实需要查看结构时，才在二级界面考虑“对话节点”等表达，不把阶段时间线常驻在 Top 1 对话页。

---

## 8. 用户控制与确认边界

以下行为默认由用户显式确认或触发：

- 增加 Skill 角色；
- 移除 Skill 角色；
- 把个人背景带入会话；
- 使用敏感资料；
- 发起交叉讨论；
- 保存正式成果；
- 归档/删除会话；
- 高风险现实操作或外部提交。

系统可以提供推荐、理由和快捷操作，但不能用“智能自动化”为由跳过关键控制权。

## 9. Top 1 对话页的产品结构

当前 UI 设计基准设备：**Xiaomi 14 Ultra，Android 竖屏，1440 × 3200 px**。

Top 1 页面优先级：

1. **消息内容**：占据绝大多数屏幕空间；
2. **角色身份**：头像、名字和发送者清晰；
3. **当前参与角色**：能看见，但不做成大型控制面板；
4. **输入区**：文本、附件/工具、@角色、发送；
5. **增加 Skill 角色**：容易找到；
6. **二级能力**：联网、思考强度、资料、交叉讨论、保存成果等收纳到工具面板或 Bottom Sheet。

视觉不得通过：

- 角色卡片大小；
- 皇冠/队长标识；
- 固定第一位；
- “主/副”标签；

暗示某个参与角色全面领导其他角色。

## 10. 与历史 PR08 模型的映射

| PR08 模型 | 当前模型 | 处理方式 |
|---|---|---|
| 问题是入口 | 用户消息/新会话入口 | 保留“直接表达问题”的价值，但不要求先创建议题 |
| Skill 是用户正式上位词 | Skill 是内部能力；Skill 角色是用户侧参与者 | 重新分层 |
| 议题是持续容器 | 会话是持续容器 | 用户侧替换；内部数据可渐进迁移 |
| 阶段是正式推进节点 | 内部可选节点 | 不再作为核心用户心智 |
| 推进议题是唯一入口 | 继续深入 | 覆盖旧冻结术语 |
| 当前 Skill 阵容 | 参与 Skill 角色 | 去编队/层级语义 |
| 邀请 Skill | 增加 Skill 角色 | 正式改名 |
| 多 Skill 默认独立回应 | 多角色默认独立回应 | 保留并强化为强契约 |
| 显式交叉讨论 | 交叉讨论 | 保留 |
| 人物型 Skill 需 AI 披露 | 真实人物型 Skill 角色需适当披露 | 保留身份真实性，同时允许更强人物感 |
| 圆桌是多 Skill 协作形式 | 多角色对话/交叉讨论 | 不作为 Top 1 产品心智 |
| 资料与成果严格区分 | 资料与成果严格区分 | 保留 |
| 用户确认正式成果 | 用户确认正式成果 | 保留 |

## 11. 不受本次变更影响的既有原则

以下原则仍有效：

- 本地优先和用户数据控制；
- BYOK Key 不应被文档或仓库泄露；
- 资料、草稿和正式成果保持区别；
- 高风险内容需要来源、时效、适用条件与专业复核边界；
- 用户拥有最终决定权；
- 删除、导入导出、恢复快照等数据安全动作需要明确确认；
- 系统不能把 AI 生成草稿自动声明为用户的正式结论。

这些领域的详细历史规格继续由相关 security/planning 文档提供；如果它们与 ADR-009 的用户术语发生冲突，术语按当前契约迁移，安全语义本身不自动失效。
