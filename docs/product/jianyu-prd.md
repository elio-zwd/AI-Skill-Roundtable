## 1. 产品身份

```text
产品 / App：见域
口号：看见更多观点，打开认知边界
当前仓库：AI-Skill-Roundtable
applicationId / namespace：com.elio.jianyu
目标设备方向：Android 手机优先
当前 UI 设计基准：Xiaomi 14 Ultra，竖屏 1440 × 3200
```

### 1.1 一句话定义

**见域是一款以 AI Skill 角色对话为核心的个人思考与行动应用。用户可以和一个或多个具有独立人格、思维方式与能力边界的 Skill 角色持续交流，在不同观点之间形成自己的判断，并把有价值的内容沉淀为资料、下一步和成果。**

### 1.2 核心差异

见域不是：

- 普通 ChatGPT 换一套头像；
- 需要用户先理解 Agent/多智能体/编排器的技术工具；
- 一个主 AI 指挥多个副 AI 的团队模拟器；
- 默认强行安排正方和反方的辩论器；
- 以“议题/阶段/流程卡”为主体的项目管理应用。

见域要做到：

- **角色真实可感知**：每个 Skill 角色有明确身份、人格、思维习惯和表达方式；
- **观点真实独立**：多个角色默认独立形成判断，不因为回答顺序而互相复制；
- **用户随时控制**：用户可以增加角色、@某个角色、发起交叉讨论、带入资料或保存成果；
- **聊天始终是主体**：高级能力服务对话，不把主页面变成控制台。

## 2. 目标用户与优先场景

### 2.1 目标用户

优先面向：

1. 希望从不同思维方式获得启发的个人用户；
2. 职场、学习与研究用户；
3. 需要做判断、规划或复盘的用户；
4. 内容创作者与知识工作者。

### 2.2 核心场景

- “我想先听一个擅长这个问题的角色怎么看。”
- “再增加一个不同思维方式的人，但不要让他照着前一个人的答案说。”
- “@某个角色，只问他这个细节。”
- “让这几个角色针对一个分歧交叉讨论。”
- “把这份资料给他们看，再继续聊。”
- “把刚才最有价值的结论保存成行动方案/知识笔记。”
- “过几天重新打开这段会话继续。”

### 2.3 核心价值

- **现实支持**：帮助用户处理生活、学习和工作中的具体问题，形成计划、沟通、研究、判断和下一步。
- **思维拓展**：通过不同 Skill 角色自身的认知方式、经验模型和价值取向，发现盲区、条件和不同路径。

“思维拓展”不等于系统强制制造反方。角色有权在独立判断后赞同其他角色。

## 3. 正式产品对象

| 对象 | 用户侧定义 | 关键边界 |
|---|---|---|
| 对话 | Top 1 核心页面，用户与 Skill 角色交流的主要空间 | 不是多智能体控制台 |
| 会话 | 可持续保存和继续的一段对话 | 替代旧用户侧“议题”心智 |
| Skill | 内部能力包/能力载体 | 不要求作为普通用户看到的参与者名称 |
| Skill 角色 | 用户实际交流的 AI 角色 | 不是无人格工具，也不冒充真人本人 |
| 消息 | 用户、角色或系统产生的时序内容 | 不自动成为成果 |
| 资料 | 用户选择带入的输入和依据 | 与成果区分 |
| 个人背景 | 用户主动保存并可选择带入的长期背景 | 不是系统暗中画像 |
| 成果 | 用户明确确认保存的可复用输出 | 普通回复不是正式成果 |
| 交叉讨论 | 用户显式触发的角色间观点互动 | 不是默认模式或无限辩论 |
| 对话节点 | 可选二级/内部结构，用于必要的长会话组织 | 不作为 Top 1 必学概念 |
| 执行运行/响应批次 | 工程内部模型调用概念 | 不作为普通用户文案 |

## 4. V1 产品范围

### 4.1 纳入 V1

- Top 1“对话”页面；
- 新建和继续会话；
- 单 Skill 角色对话；
- 多 Skill 角色对话；
- Skill 角色搜索、分类、推荐、详情、收藏与最近使用；
- 增加/移除 Skill 角色；
- `@角色` / 本次回复角色；
- 默认独立回应；
- 用户显式交叉讨论；
- 自由追问；
- 继续深入；
- 联网搜索、思考强度等高级生成能力；
- 资料和个人背景按用户确认带入；
- 保存为成果；
- 资料与成果全局入口；
- 会话记录、搜索、归档、恢复和删除；
- 停止、重试、部分成功和进程恢复；
- 官方 Skill/Skill 角色持续完善；
- 本地数据、安全导入导出与恢复机制按对应安全规格推进。

### 4.2 V1 不纳入

- 用户随意修改官方角色系统提示词；
- 第三方未审查 Skill/角色执行代码导入；
- 公开 Skill 市场；
- 自动把系统建议的角色加入会话并直接开始调用；
- 自动替用户完成现实审批、签署、付款、提交等高风险动作；
- 通过 UI 暗示某个 Skill 角色是真人本人在线；
- 默认让新增角色服从前一个角色；
- 默认强制正反方辩论；
- 无限制自动角色互聊。

## 5. Top 1 核心页面：对话

### 5.1 页面目标

用户进入见域后，应最快完成两件事之一：

1. 继续最近会话；
2. 和某个 Skill 角色开始一段新对话。

聊天内容必须是页面绝对主体。

### 5.2 页面主结构

从上到下建议包含：

1. **系统状态栏**；
2. **顶部会话栏**：会话记录入口、当前会话标题、新建会话、更多；
3. **Skill 角色区域**：参与角色头像/名称，以及“增加 Skill 角色”；
4. **消息区**：用户消息与各 Skill 角色消息；
5. **输入区**：附件/工具、文本、@角色、发送/停止；
6. **底部一级导航**：当前项为“对话”，其他入口以后续 IA 规格为准。

### 5.3 角色区域规则

- 所有参与 Skill 角色视觉身份清晰；
- 多个角色之间不使用“主/副”标签；
- 不通过皇冠、队长、明显更大的头像等表达默认权力；
- 排序可以基于加入时间、最近互动或用户选择，但排序本身不表示角色地位；
- 增加角色的正式按钮文案为 **增加 Skill 角色**。

### 5.4 消息规则

每条角色消息至少让用户知道：

- 谁说的；
- 角色头像；
- 角色名；
- 正文；
- 必要的来源/引用入口；
- 失败/停止/重试状态。

不同角色不应全部被折叠为统一的“AI”头像和署名。

消息级动作可包括：

- 复制；
- 保存为成果；
- 引用/基于此继续；
- 重试/重新生成；
- 查看来源；
- 更多。

手机端避免每条消息常驻一排大量按钮。

### 5.5 输入区规则

必须支持：

- 多行文本；
- 发送；
- 生成中停止；
- `@Skill 角色`；
- 附件/资料入口；
- 工具面板。

联网搜索、思考强度、参考资料、交叉讨论等高级选项不应常驻占用大量高度。启用后可以使用紧凑状态 Chip 表达。

### 5.6 主屏禁止长期展示

- “议题”作为页面标题或最高层对象；
- “推进议题”主按钮；
- 主 Skill / 副 Skill；
- Run ID、执行历史、Interaction ID；
- 持久化/上下文确认等工程术语；
- 大型阶段时间线；
- 大型策略控制卡；
- 为展示功能而展开全部工具。

## 6. Skill 角色体系

### 6.1 用户侧统一认知

**只要它会作为参与者和用户说话，它就是 Skill 角色。**

Skill 是内部能力概念，角色是用户体验概念。

Skill 角色可来自：

- 真实人物启发/模拟；
- 专业角色；
- 思维方法角色；
- 任务型角色；
- 其他具有稳定身份和表达方式的官方角色。

纯工作流/工具如果不需要作为独立说话者出现，应挂在角色能力层，不为了分类完整而硬做成“人”。

### 6.2 角色详情

至少展示：

- 名称；
- 头像/肖像；
- 一句话定位；
- 擅长领域；
- 思考特点；
- 适合的问题；
- 可能的局限；
- 联网/资料要求；
- 来源与时效提示；
- 如为真实人物型角色，AI 模拟身份说明；
- “开始对话 / 增加到当前会话”等动作。

### 6.3 角色感设计原则

角色能力发挥需要足够的人格一致性：

- 视觉上可以接近真人角色；
- 使用明确姓名，不要求使用“XX Skill 工具”这类机械命名；
- 允许第一人称自然表达；
- 对同类问题保持稳定思维习惯；
- 不应因为安全提示把每条消息都写成模板化免责声明。

### 6.4 真实人物型角色身份边界

统一采用类似：

> AI 模拟角色，基于可获得资料构建，不代表本人，也不保证复现本人当前或完整观点。

建议出现位置：

- 角色详情；
- 第一次加入/开始对话时的轻量提示；
- 高风险场景必要提示。

不得把 AI 生成内容伪装成真实人物本人此刻真实发言、授权、背书或决定。

## 7. 单角色、多角色与独立判断

### 7.1 单角色会话

单角色会话应接近高质量一对一 AI 对话体验。

用户随时可以 **增加 Skill 角色**，不需要把会话“升级成另一种模式”。

### 7.2 多角色会话

多个参与角色：

- 平级；
- 独立；
- 共享用户明确允许的必要上下文；
- 不共享默认领导关系；
- 不固定站队。

多角色是同一会话的自然状态，不需要把用户带进“阵容管理”心智。

### 7.3 默认独立回应

多角色最重要的质量指标之一，是新增角色是否真的给出**自己的判断**。

默认输入优先级：

1. 用户当前问题；
2. 当前必要用户消息；
3. 用户选择的资料；
4. 用户选择的个人背景；
5. 角色自身 Skill 设定；
6. 必要的中性事实简报。

其他 Skill 角色的生成结论默认不是新角色必须继承的前提。

#### 验收要求

在相同用户问题下：

- 角色 B 不应只是改写角色 A 的答案；
- 角色 B 可以自然得出与 A 相同的结论，但必须体现自己的推理路径/条件；
- A 的先后发言顺序不应系统性决定 B 的立场；
- 如果隐藏 A 的回答，B 的核心判断不应出现无法解释的剧烈改变（除非用户明确要求其评价 A）。

### 7.4 `@角色` / 本次回复角色

用户点名角色只影响当前请求。

例如：

> `@费曼 你觉得这里最关键的假设是什么？`

这不会：

- 让费曼成为主角色；
- 移除其他角色；
- 修改长期默认领导关系（因为不存在该关系）。

### 7.5 增加 Skill 角色

新增角色流程应说明它的角色能力，而不是把它描述成“被邀请来支持当前主 Skill”。

角色加入后第一次回答：

- 应基于自己的思维方式；
- 可以赞成、补充、反对或暂不下结论；
- 不默认承担“反方”；
- 不默认读取所有其他角色完整历史输出。

## 8. 交叉讨论

### 8.1 触发

交叉讨论必须由用户显式发起。

用户可以选择：

- 参与角色；
- 讨论焦点；
- 当前消息/某条观点/最近上下文；
- 可选讨论深度。

### 8.2 行为

交叉讨论时，角色可以明确看到其他参与角色的相关观点，并进行：

- 赞同并补充；
- 质疑；
- 澄清前提；
- 比较适用条件；
- 找到证据分歧；
- 收敛下一步。

### 8.3 结束

交叉讨论完成后默认恢复独立回应。

系统可整理：

- 共识；
- 分歧；
- 各自依据；
- 适用条件；
- 仍待确认的信息；
- 用户下一步。

不得通过多数票自动宣布某个角色“获胜”或某个观点是真理。

---

## 9. 继续深入

旧规格的“推进议题”不再是唯一正式用户入口。

当前正式自然动作：**继续深入**。

它可以根据当前对话提供建议：

- 深挖当前问题；
- 检查关键假设；
- 增加一个不同 Skill 角色；
- 发起交叉讨论；
- 搜索/核查资料；
- 整理可执行下一步；
- 保存为成果。

“继续深入”不要求每次创建一个用户可见的新阶段。

如果某些工作流确实需要阶段/步骤，阶段可以是该工作流自己的局部概念，而不是整个 App 的最高层结构。

## 10. 资料、个人背景与成果

### 10.1 资料

用户可以：

- 上传/选择资料；
- 查看当前会话使用了哪些资料；
- 移除本次使用；
- 在必要时查看来源。

角色使用资料时要保留来源和适用范围。

### 10.2 个人背景

个人背景必须：

- 用户可见；
- 用户可编辑；
- 用户可选择是否用于当前会话；
- 不因系统推断而自动成为长期事实。

### 10.3 成果

用户可从消息或会话中保存成果。

典型成果：

- 决策记录；
- 行动方案；
- 知识笔记；
- 沟通稿；
- 研究摘要；
- 可交付文档；
- 音频等派生形式。

**只有用户明确确认保存后才是成果。**

---

## 11. 会话记录与生命周期

会话状态至少支持：

```text
新建 → 活跃 → 继续 → 归档 → 恢复 / 删除
```

要求：

- 自动生成或用户编辑标题；
- 可搜索历史会话；
- 归档不等于删除；
- 删除展示影响范围；
- 重新打开会话能够继续对话；
- 角色参与变化和历史消息保持可追溯。

用户需要完全独立的新主线时，直接新建会话即可，不需要理解“关联新议题”。如果未来需要建立会话之间的引用关系，可以作为高级功能设计。

## 12. 推荐与发现

### 12.1 推荐原则

系统可以根据用户当前问题推荐 Skill 角色，但推荐必须：

- 有理由；
- 能看懂角色适合解决什么；
- 明确限制；
- 不因为“多样性”强行塞一个反方；
- 不自动加入并调用；
- 允许用户忽略。

### 12.2 推荐理由

推荐理由优先写角色与用户问题的匹配：

- 擅长什么；
- 会从什么角度思考；
- 可能补足什么盲区；
- 需要什么资料；
- 有什么风险/时效限制。

避免工程语言：

- “加入 Agent 阵容”；
- “增强多智能体覆盖度”；
- “优化路由 diversity score”。

---

## 13. 模型调用与上下文隔离要求

### 13.1 产品契约高于优化实现

Interactions API、缓存、摘要、向量召回等都可以用于优化，但不得破坏角色独立性。

尤其需要审计：

- `previous_interaction_id` 是否跨角色串联；
- fallback 全量历史 prompt 是否无差别包含其他角色输出；
- 摘要是否把角色 A 的判断写成“已确认事实”；
- 路由/编排是否默认让后一个角色只补充前一个角色。

### 13.2 推荐的逻辑隔离

角色独立回应可以采用：

```text
共享：用户事实 / 用户消息 / 用户确认资料 / 中性会话背景
隔离：每个角色自己的 persona / 推理链路 / 模型会话链
按需共享：其他角色的具体观点（用户引用或交叉讨论）
```

具体实现方式不在本 PRD 冻结，但最终行为必须满足独立性验收。

---

## 14. 错误、停止与恢复

- AI 生成中可以停止；
- 单个角色失败不应让其他已成功回答消失；
- 失败显示在对应角色消息位置并支持重试；
- 重试应说明是重试该角色还是本次全部请求；
- App 进程恢复后尽量保留已完成消息、输入草稿和附件选择；
- 工程错误信息转换为用户可理解文案，不直接展示内部 Run/Stack/Interaction ID。

## 15. 安全与高风险边界

本次产品心智模型调整不削弱既有安全目标。

### 15.1 真实人物型角色

- 必须说明 AI 模拟身份；
- 可以高度拟人化；
- 不得伪造真人实时发言、授权或背书。

### 15.2 专业高风险问题

医学、法律、金融等场景：

- 区分一般信息与正式专业意见；
- 核对来源和时效；
- 明确不确定性与适用条件；
- 重要决定建议专业人员复核；
- 紧急人身安全情况优先现实帮助。

### 15.3 用户数据

- 本地优先目标保持；
- 长期个人背景需要用户确认；
- 敏感资料不能默认发送给所有角色；
- 导入/导出/恢复/删除等高影响动作遵循对应安全规格。

## 16. 信息架构约束

目前只冻结一个最高优先级：**对话是 Top 1 核心页面。**

其他一级页面仍可在后续 UI 重组中继续调整，不应因为历史 PR08 导航结构而提前锁死。

当前推荐保留的能力域：

- 对话；
- Skill 角色发现/管理；
- 会话记录；
- 资料与成果；
- 设置。

这些能力最终是否全部成为独立底部导航项，由后续 IA/UI 规格决定。

## 17. UI 设计基准

本轮移动 UI 重构只以：

```text
设备：Xiaomi 14 Ultra
平台：Android
方向：竖屏
设计画布：1440 × 3200 px
语言：简体中文
```

为主要设计基准。

设计必须体现：

- Android 而非 iOS 视觉/系统行为；
- 中央挖孔和系统状态栏安全区；
- 底部手势区域；
- 窄长屏上的可读宽度；
- 聊天内容优先；
- 单手可触达的常用操作。

## 18. 验收标准

### 18.1 概念验收

新用户看到 UI 后，应自然理解：

> “我正在和几个不同的 AI Skill 角色聊天。”

而不是：

> “我在操作一个议题编排工作台。”

### 18.2 多角色验收

- 用户看不出固定主从关系；
- 新增角色不会被默认标成反方；
- 每个角色有清楚的身份；
- 多角色回答存在真实思路差异而非改写复读；
- 只有显式交叉讨论才出现角色互评/互辩。

### 18.3 人物感验收

- 角色有足够稳定的视觉与表达身份；
- 真实人物型角色可产生人物感和沉浸感；
- 用户仍能在合理位置知道它是 AI 模拟角色；
- 主聊天流不被免责声明反复打断。

### 18.4 主页面验收

- 消息区占据绝大多数可用空间；
- 角色身份清晰；
- 增加 Skill 角色容易找到；
- @角色和输入方便；
- 高级控制项默认收起；
- 不出现“议题/推进议题/主 Skill/邀请 Skill”等旧核心文案。
