# ADR 009 — “对话 + Skill 角色”产品心智模型与多角色独立性

## 1. 背景 (Context)

PR08 期间，“见域”曾将用户侧最高层业务对象定义为“议题”，将 Skill 定义为统一能力载体，并围绕“议题 → 阶段 → 推进议题”组织主要产品流程。这套定义帮助工程从旧的聊天/轮次模型向更完整的数据模型演进，但在后续 UI 重构审查中暴露出明显的用户心智负担：

1. **“议题”不符合 Top 1 使用行为**：用户最常做的事情不是管理一个抽象“议题容器”，而是直接和一个或多个 AI 角色持续对话。
2. **“Skill”在用户侧过度工具化**：内部的 Skill 确实是能力载体，但用户实际面对的是具有姓名、头像、稳定人格、思维方式和表达方式的角色。把用户界面中的参与者仅称为 Skill，会削弱角色表现力和沉浸感。
3. **“邀请 Skill / 主 Skill / 反方”容易制造错误关系**：增加第二个角色并不意味着它受第一个角色领导，也不意味着它天然承担反方职责。每个角色都应作为平等、独立的判断主体参与。
4. **默认共享其他角色结论会导致锚定与过早收敛**：旧规格已经要求“多 Skill 默认独立回应”，本 ADR 将这一原则进一步提升为用户侧和执行侧共同遵守的产品契约。
5. **“不能冒充真人”不等于“不能做得像真人”**：用户知道角色由 AI 驱动。角色可以高度人格化、拟人化并使用人物肖像/姓名/第一人称表达；对于基于真实人物的角色，需要在合适位置明确 AI 模拟身份，但不应在每条消息中重复打断沉浸感。

本 ADR 是 2026-08-29 后续产品决策。它**明确覆盖** PR08 文档中与下述新定义冲突的冻结项；历史 PR08 记录保留用于追溯，不再作为冲突处的当前产品真相。

## 2. 决策 (Decisions)

### 2.1 Top 1 心智模型改为“对话”

用户侧一级核心页面正式名称为：**对话**。

用户长期保存并可继续的对象正式名称为：**会话**。

“议题”不再作为普通用户必须理解的最高层产品对象，也不再作为 Top 1 页面、列表和主要动作的正式名称。工程内部如仍需要 `topic`、`stage` 等结构完成迁移，可以暂时保留，但不能反向要求用户学习这些内部概念。

### 2.2 区分内部 Skill 与用户侧 Skill 角色

- **Skill**：内部能力包/能力载体，可包含角色提示词、领域知识、工具权限、工作流和输出能力。
- **Skill 角色**：用户在对话中实际感知和交互的 AI 角色，是 Skill 能力的角色化呈现。

用户界面、产品文案和视觉设计中，只要指代“正在和用户交流的参与者”，统一使用 **Skill 角色** 或具体角色名称，不再把它表现成无人格的工具条目。

纯工具/工作流能力如果不需要作为独立对话主体出现，应作为 Skill 角色可调用的能力或工具存在，而不是为了统一分类而伪装成一个人物。

### 2.3 角色可以高度拟人化，但身份必须真实

Skill 角色应允许：

- 使用人物化头像或肖像；
- 使用稳定姓名和角色身份；
- 保持持续的人格、价值取向、思考方式和表达风格；
- 使用自然的第一人称交流；
- 在不同会话中保持角色设定的一致性。

对于基于真实人物构建的 Skill 角色：

- 可以使用人物化名称、肖像和风格来提升角色表现；
- 必须在角色详情、首次使用或其他合理位置说明其为 **AI 模拟角色/视角**，不代表本人，也不保证复现本人当前或完整观点；
- 不需要在每条消息中重复免责声明；
- 不得把生成内容表述为真实人物本人实际说过、实际批准或实际作出的当前建议，除非有可核验来源明确支持该事实。

### 2.4 所有参与角色平级，不存在默认主从关系

一个会话中的多个 Skill 角色默认是**平等、独立的参与者**：

- 不设置“主 Skill / 副 Skill”产品关系；
- 不因为加入顺序产生领导关系；
- 不因为 UI 排序、头像大小或位置表达权力高低；
- 不默认分配“正方 / 反方 / 支持者 / 质疑者”等相对职责；
- 角色是否赞同、补充或反驳其他观点，应由它自己的角色设定、知识、证据和推理自然产生。

组合层可以保存角色集合和用户明确配置的任务分工，但这不改变角色之间的平级身份，也不能让一个角色“全方面领导”其他角色。

### 2.5 “邀请 Skill”改为“增加 Skill 角色”

用户动作正式名称为：**增加 Skill 角色**。

“邀请 Skill”退出正式用户文案，因为该词容易暗示社交邀请或既有团队关系，也无法准确表达用户是在当前会话中增加一个新的独立 AI 角色。

增加角色后：

- 既有消息不会删除或改写；
- 新角色不会自动成为任何既有角色的从属；
- 新角色不会自动被赋予反方或补充者身份；
- 用户可以随后移除角色，历史回答仍保留。

### 2.6 默认独立回应是强产品契约

多角色会话中，**独立回应优先于角色互相参考**。

默认情况下，一个 Skill 角色形成本轮首次判断时，应主要基于：

- 用户当前问题和用户消息；
- 用户明确选择带入的资料、背景和成果；
- 该角色自己的角色设定、知识和能力；
- 为保持会话连续性所需的中性事实上下文。

默认不应把其他 Skill 角色刚刚生成的结论、措辞或完整回答作为它的领导性上下文，以避免锚定、复读、从众和过早收敛。

如果用户主动引用另一角色的消息、明确要求评价某角色观点，或进入“交叉讨论”，则可以把相关角色输出作为明确输入。

### 2.7 交叉讨论必须显式触发

正式名称保留：**交叉讨论**。

只有用户显式触发时，参与角色才进入“互相看到并回应彼此观点”的协作方式。用户应能够选择参与角色和讨论焦点。

交叉讨论：

- 不改变角色长期身份；
- 不产生主从关系；
- 不以多数票决定真理；
- 不自动无限循环；
- 结束后默认恢复各角色独立判断。

### 2.8 定向回复只影响当前请求

用户可以通过 `@角色` 或“本次回复角色”选择，让某个 Skill 角色回答当前请求。

这只改变当前回复对象：

- 不把该角色提升为主角色；
- 不移除其他角色；
- 不改变会话长期参与关系；
- 不让其他角色以后自动服从它的判断。

### 2.9 “推进议题 / 阶段”退出核心用户心智

“推进议题”不再是冻结的用户侧正式入口。

当需要把当前对话整理成后续方向时，用户侧优先使用：**继续深入**。

如果内部数据仍需要保存阶段/节点关系，可使用内部 `stage`，或在确有必要的二级界面使用“对话节点”等较自然表达；不能让阶段时间线压过聊天本身。

### 2.10 UI 设计必须强化“角色”，而不是“工具”

Top 1 对话页应满足：

- 聊天正文是绝对主体；
- 角色头像、名称、身份和消息署名清晰；
- 多角色视觉权重平等；
- “增加 Skill 角色”明显但不抢占聊天空间；
- 高级控制项收进二级入口/Bottom Sheet，不把页面做成多智能体控制台；
- 当前移动端 UI 设计基准为 Xiaomi 14 Ultra 竖屏 1440 × 3200。

## 3. 术语覆盖关系

| PR08/历史用户术语 | 当前正式用户术语 | 说明 |
|---|---|---|
| 议题 | 会话 | 用户持续保存和继续的对话容器 |
| 议题列表 | 会话记录 | 历史/持续会话入口 |
| 议题详情 / 工作区 | 对话 | Top 1 核心页面 |
| Skill（指对话参与者） | Skill 角色 | Skill 仍可作为内部能力概念 |
| 当前 Skill 阵容 | 参与 Skill 角色 | 不暗示编排阵容或等级 |
| 邀请 Skill | 增加 Skill 角色 | 新角色为平级独立参与者 |
| 主 Skill / 副 Skill | 不使用 | 可用“本次回复角色”表达一次性定向 |
| 正方 / 反方（默认角色） | 不使用 | 立场由角色独立判断自然形成 |
| 推进议题 | 继续深入 | 需要时再进入后续整理流程 |
| 阶段（一级用户概念） | 不作为一级概念 | 内部可保留；必要时二级称“对话节点” |
| 临时定向回应 | @角色 / 本次回复角色 | 只影响当前请求 |
| 显式交叉讨论 | 交叉讨论 | 仍须用户主动触发 |

## 4. 后果与实施要求 (Consequences)

### 正向影响

- 用户打开 App 后无需学习“议题 / 阶段 / 多智能体编排”等抽象概念即可开始核心行为；
- Skill 的人物设定和思维差异能够在 UI 与生成结果中被充分感知；
- 多角色不再被错误设计成“一个主角色带一组副手”；
- 默认独立回应降低角色之间复读、锚定和虚假共识；
- 后续 UI 可以更接近高质量即时对话产品，同时保留见域的多角色差异化能力。

### 迁移要求

- 产品文档与用户文案优先按本 ADR 更新；
- 历史 PR08 计划/决策文档保留，不需要逐份重写，但发生冲突时以本 ADR 和更新后的 `docs/product/` 当前文档为准；
- Kotlin/Room/Route 等内部名称不要求在本 ADR 所在 PR 中立即重构；
- 后续 UI PR 应逐步清理“议题”“邀请 Skill”“主 Skill”等用户可见旧文案；
- 编排层后续需要审计上下文传递，确保“独立回应”不会因为共享前一角色完整输出而被实现层破坏。

## 5. 状态

**Accepted** — 2026-08-29。
